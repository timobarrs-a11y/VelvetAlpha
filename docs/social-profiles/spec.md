# Social Profiles & Progress Feed — Spec

Status: draft for review · Owner: Timo · Last updated: 2026-10-20

## 1. What we're building

Open VelvetAlpha up so members can see each other's progress. Every member gets a
public profile (avatar only — no face photos) showing their shared goals and
progress. When they do something — finish a commitment, hit a streak, complete a
plan step — the app posts it for them automatically as a reward. Other members
can like, comment, follow, and discover each other by shared goals or by what's
trending. Atlas can introduce members working on the same things.

The loop this closes: the small retention mechanics (streaks, check-ins,
commitments, milestones) stop being private bookkeeping and become something
other people see and respond to.

### Principles

1. **Action is the content.** Most posts are generated by doing, not writing.
2. **Avatars, never faces.** No photo uploads anywhere on the profile.
3. **Public by choice, field by field.** Only the fields in §3 can ever be
   public. Nothing from journals, coaching chat, memories, insights or
   location ever leaves the private layer.
4. **Paying or trial members, ID-verified adults only.** Every social surface is
   gated server-side (§2).
5. **Bots are disclosed.** Bots like and comment as part of the system; the site
   says so, and bot accounts are labeled on their profiles and comments.

## 2. Access gate: paid or trial + ID-verified 18+

### Current state (gaps found in the code)

| Finding | Where |
|---|---|
| Free and trial tiers exist; new users default to `free`. | `user_profiles.subscription_tier` default, `src/types/subscription.ts` |
| Age check is a client-side checkbox: the browser writes `age_verified_at = now()` at signup. | `src/pages/SignUpPage.tsx:116`, `src/services/authService.ts:43` |
| `age_verified_at` and `birthday` are in the client-writable column grant, so any user can set them directly. | `20261009131910_restrict_user_profiles_privileged_columns.sql` |
| `AgeVerificationModal.tsx` exists but nothing renders it. | `src/components/AgeVerificationModal.tsx` |

### Design

- **Who gets in.** Members on a paid tier (essential, plus, elite) or an active
  trial.
- **Age verification uses ID, required at launch.** Use Stripe Identity: Stripe
  is already integrated (`stripeService`, `stripe-webhook`), and it handles
  document plus selfie checks.
  - The check runs the first time a member opens any social surface, not at
    signup. This keeps signup friction unchanged and only pays the
    per-verification fee for people who want social.
  - New edge function `create-identity-session` creates a Stripe Identity
    VerificationSession and returns the client secret.
  - `stripe-webhook` handles `identity.verification_session.verified`:
    - reads the verified date of birth,
    - rejects anyone under 18,
    - writes `id_verified_at`, `birthday` and `age_verified_at` server-side.
  - Store only the verified status and DOB. ID images and selfies stay with
    Stripe and are never shown anywhere in the app.
  - On failure (`requires_input`), the member can retry. After 3 failed attempts,
    their case goes to the admin console queue.
- **Lock down the existing columns.**
  - Revoke client `UPDATE` on `age_verified_at` and `birthday`, and add
    `id_verified_at` as a server-only column.
  - The signup checkbox stays as the 18+ attestation for the private app, but it
    no longer satisfies the social gate.
- **Single gate function** used by every social table's RLS and every social
  edge function:

  ```sql
  can_use_social(uid uuid) RETURNS boolean
  -- true when:
  --   (subscription tier is essential | plus | elite OR an active trial)
  --   AND id_verified_at IS NOT NULL (set only by the Stripe Identity webhook)
  --   AND NOT is_banned
  ```

- **Lapsed access.** When a subscription or trial lapses, the profile and posts
  are hidden from others (not deleted) and come back on renewal. ID
  verification is kept and doesn't have to be redone.

## 3. Public profile

Extend the existing `im_discovery_profiles` table, which is already the public
projection used by IM discovery. Do **not** expose `user_profiles`: it stays
owner-read-only.

| Field | Source | Notes |
|---|---|---|
| `display_name` | user-entered | Defaults to `nickname`. |
| `avatar_config` | snapshot of `user_profiles.avatar_config` | Rendered with the existing avatar system. Drop or lock `avatar_url` so it can only point at our generated avatar renders, never an upload. |
| `headline` | user-entered | Existing column. |
| `gender` | copied on opt-in | New column plus `show_gender boolean default false`. |
| `interests` | user-picked | Existing column. |
| Shared goals | `social_shared_goals` | See below. |
| Posts | `social_posts` | See §4. |

Nothing else. Public fields are copied into the public table only when the user
saves their profile; there are no views or joins from public tables into
`user_profiles`.

### Shared goals

`social_shared_goals (user_id, goal_id → user_goals, auto_post boolean, show_details boolean, created_at)`

- Sharing is per goal. Nothing is shared by default.
- Public goal fields: `title`, `goal_type`, `current_value`, `target_value`,
  `unit`, `target_date`, `status`, and the streak. `notes` is never public.
- `show_details` (default false) controls whether commitment and plan-step
  titles appear in auto-posts (§4).

## 4. Auto-posts (progress as reward)

### Triggers

Database triggers write an event to `social_post_events`. A worker turns events
into posts. A trigger fires only if the related goal is in
`social_shared_goals` with `auto_post = true`.

| Event | Source |
|---|---|
| Commitment completed | `coaching_commitments.status → 'completed'` (must have `goal_id`) |
| Plan step completed | `coach_plan_steps.completed_at` set (plan linked to a shared goal) |
| Goal completed | `user_goals.status → 'completed'` |
| Goal progress milestone | `user_goals.current_value` crosses 25 / 50 / 75 % |
| Streak milestone | Check-in streak hits 3, 7, 14, 30, 60, 100, 180, 365 |
| Achievement unlocked | `milestone_achievements` insert (rarity uncommon or higher) |

Commitments with no `goal_id` never post. They come from chat extraction and
may be private.

### Post content

- Generated from **templates**, not from chat text. Never use
  `coaching_commitments.extracted_from_message`, and use `description` only when
  `show_details = true`.
  - Default example: "Completed a step toward **Run a 5K** · 🔥 12-day streak"
  - With details: "Completed **'Run 3km without stopping'** toward **Run a 5K**"
- The user can add an optional one-line note afterwards.
- Several events on the same goal within 6 hours are bundled into one post.
- At most 3 auto-posts per user per day; overflow is bundled into a daily recap.
- The user's first auto-post shows a one-time toast: "We shared this to your
  profile" with **Undo** and **Turn off for this goal**.
- Any post can be deleted. Deletion is a soft delete, and the post is hidden
  immediately.

### Manual posts

Members can also write a free-text post (optionally linked to a shared goal).
Same moderation as comments (§7).

## 5. Likes

### Behavior

- One reaction type: **like**.
- Public display is the **count only**. Everyone who can see a post sees its
  like count. The list of who liked is not shown to anyone, including the
  author.
- Likes come from members and from bots. Both count the same toward the
  displayed total.

### Data

`social_likes (post_id, liker_id, liker_kind 'human'|'bot', created_at, UNIQUE(post_id, liker_id))`

`liker_kind` is internal: it's used for metrics (§11) and for ranking (§8), and
isn't shown in the UI.

### Bot likes

- **Bot accounts.** Bots are labeled accounts using the existing pattern
  (`auth.users.raw_app_meta_data.is_bot = true`, as with Maya and Jordan in
  `community_bot_infrastructure`). Each has an interest profile.
- **Matching.** A bot likes a post when the post's goal type or interests match
  its profile.
- **Momentum.** Each author has a like budget that grows with:
  - account age and number of posts,
  - real engagement (human likes, comments, follows),
  - the size of the milestone (a 100-day streak earns more than a first
    check-in).

  A first post gets a few likes; budgets ramp over weeks. Default curve:

  | Author's post # | Bot likes per post |
  |---|---|
  | 1–3 | 1–4 |
  | 4–10 | 3–10 |
  | 11–30 | 5–20 |
  | 30+ | Grows with human engagement, up to the per-post cap |

  Big milestones (goal completed, a 30+ day streak) get up to 2× the range. The
  per-post cap defaults to 60.

- **Settings.** The curve, milestone multiplier and cap live in `app_settings`
  under the key `social_bot_like_budget`, so they can be tuned from the admin
  console without a deploy.

- **Delivery.** Likes are spread over hours, front-loaded the way organic
  engagement is, not dropped in all at once.
- **Runner.** A new `social-bot` edge function on cron (service role only),
  modeled on `community-bot`, logs every action to `social_bot_runs`.
- **Exclusions.** Bots never like posts flagged by moderation, posts flagged as
  crisis content (§7), or posts from users who turned bot interactions off.

### Disclosure

- A help/FAQ page ("Bots on VelvetAlpha") explains that bots like posts that
  match their interests and comment with questions.
- The Terms and Privacy Policy get the same paragraph.
- Bot profiles carry a **Bot** badge.

## 6. Question bots

Clearly labeled bot accounts that reply to posts with a probing question, to
get people reflecting and talking.

- Examples: "What made today's run easier than last week's?" or "Day 30 — what's
  one thing you'd tell yourself on day 1?"
- **Input:** the post text and the author's public profile only. No private
  data.
- **Labeling:** comments are stored with `is_ai_generated = true` and shown with
  the Bot badge.
- **Frequency:** at most one bot question per post, on roughly 1 in 3 eligible
  posts, at most 2 per user per day.
- **Never:** on crisis-flagged posts, on users who turned it off, or questions
  that are judgmental or medical/clinical.
- **Notifications:** when the author replies, the bot may answer once. The
  thread is then left for humans.
- **Prompt rules:** prompts live in `src/prompts/` with the other bot
  personalities. Questions are short (≤ 25 words), one per comment, and never
  open with praise filler.

## 7. Comments, moderation, safety

### Comments

`social_comments (id, post_id, author_id, body, is_ai_generated, created_at, deleted_at)`

Who can comment is a per-user setting:

| Setting | Who can comment |
|---|---|
| `everyone` (default) | Any member |
| `mutuals` | People who follow the author and whom the author follows back |
| `nobody` | No one |

### Moderation

- **Pre-screen.** Every human post and comment goes through the existing
  `_shared/moderation.ts` before it is visible. Blocked content is rejected
  with a reason. Borderline content is held and logged to `moderation_flags`.
- **Reports.** Extend `community_reports.target_type` with `social_post`,
  `social_comment` and `profile`, so reports reuse the existing admin console
  queue.
- **Blocks.** `im_blocks` is enforced in RLS on every social table. A blocked
  user can't see the blocker's profile, posts or comments, and can't like,
  comment, follow or DM them, in either direction.

### Crisis content

Self-harm or acute-distress signals on a post or comment:

- the post is not boosted, gets no bot likes or bot comments, and doesn't
  appear in discovery;
- the author privately sees support resources.

## 8. Follow & discovery

- **Follows:** `social_follows (follower_id, followee_id, created_at)`.
- **No counts shown.** Follower and following counts are never displayed,
  including to the profile owner. A member can see the list of people they
  follow, not a number.
- **Discovery, mode A — shared goals.** Cards like "12 people training for a 5K
  right now", built from `social_shared_goals` grouped by `goal_type` and
  normalized title. Tapping a card lists those members' profiles.
- **Discovery, mode B — trending.** Posts ranked by effort and recent
  engagement:
  - ranking signals: milestone size, streak length, human likes, comments, and
    follows from the post;
  - bot likes don't feed ranking, so bots can't decide what trends.
- **Search:** by interest and goal type.
- **Eligibility:** only profiles with `discoverable = true` and
  `can_use_social()` appear anywhere in discovery.

## 9. Atlas introductions

Atlas, not the coaches, makes the social introductions. It sees across all of a
user's coaches and goals, and the Atlas interface is the natural place for
"meet people" suggestions.

- **New tool: `find_people`.** Calls a SECURITY DEFINER function that reads
  only the public layer:
  - `im_discovery_profiles` where `discoverable`,
  - `social_shared_goals` and recent `social_posts`,

  filtered by `can_use_social()` and blocks.
- **Hard rule.** `atlas-agent` currently queries with the service-role client
  (`supabaseAdmin`), which bypasses RLS. The social tool must **not** query
  another user's `user_goals`, `coaching_*`, memories or chats through it. Any
  information about another member comes only from the public layer above.
  Enforce this in code review and with a test that seeds private data for user
  B and asserts it never appears in user A's Atlas context.
- **Suggestion style:** "Sam is also working toward a 5K and just hit a 30-day
  streak. Want to see their profile?"
- **Limits:** at most one unprompted introduction per day. Users can turn
  introductions off, and can't be suggested to others while
  `discoverable = false`.

## 10. Notifications

- Extend `community_notifications.type` with `social_like`, `social_comment`,
  `social_follow` and `atlas_intro`.
- Likes are batched: "Your 14-day streak got 23 likes" at most every few hours
  per post, not one notification per like.

## 11. Data model summary

| Table | Purpose | RLS (all require `can_use_social(auth.uid())`) |
|---|---|---|
| `im_discovery_profiles` (extended) | Public profile | Read where `discoverable` and not blocked; write own |
| `social_shared_goals` | Which goals are public | Read via profile visibility; write own |
| `social_post_events` | Trigger output queue | Service role only |
| `social_posts` | Auto and manual posts | Read if author visible and not blocked; insert own manual posts; soft-delete own |
| `social_likes` | Likes (human and bot) | Insert own human likes; expose only the count via RPC; bots insert via service role |
| `social_comments` | Comments | Read with post; insert per the author's comment setting |
| `social_follows` | Follow graph | Insert/delete own |
| `social_settings` | `comment_permission`, `bot_interactions`, `atlas_intros`, `auto_post_default` | Own only |
| `social_bot_runs` | Bot action log | Service role / admin only |

## 12. Metrics

- **Primary:** 30-day retention of members with ≥ 1 human connection (a follow,
  or a human comment or like received) vs. members with none.
- **Bot share of likes** per author over time (internal), so we can see whether
  human engagement is growing or the feed is mostly bot-driven.
- **Auto-posting:** opt-in rate, and undo/turn-off rate on first auto-post.
- **Discovery:** follows and comments that come from Atlas introductions and
  from discovery.
- **Safety:** report rate, block rate, and moderation rejections per 1k posts.

## 13. Phases

1. **Gate.**
   - Stripe Identity session and webhook handling, `id_verified_at`.
   - Revoke the client column grants, add `can_use_social()`.
   - "Verify to join the community" screen in front of every social surface.
2. **Profiles.**
   - Extend `im_discovery_profiles`, add `social_shared_goals`.
   - Profile page and editor.
3. **Auto-posts.**
   - Triggers, worker, templates, bundling, undo toast, manual posts.
4. **Likes & comments.**
   - Likes with count-only display, comments with permission settings.
   - Moderation pre-screen, reports, blocks in RLS.
5. **Bots.**
   - `social-bot` function: momentum-budgeted likes and question comments.
   - Disclosure page.
6. **Discovery & follows.**
   - Shared-goal cards, trending (human-signal ranking), search.
7. **Atlas `find_people`.**
   - The tool, the privacy test, and the introduction limits.

## 14. Decisions

| Question | Decision |
|---|---|
| Trial users get social access? | Yes |
| Follower counts visible? | No, never displayed |
| Bot-like budget | Defaults in §5, tunable in `app_settings` |
| Like counts visible on others' posts? | Yes, on everyone's posts |
| ID verification at launch? | Yes, via Stripe Identity |
