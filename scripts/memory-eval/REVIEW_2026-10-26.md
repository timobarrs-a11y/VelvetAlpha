# Memory engine adversarial review — 2026-10-26

Read-only review of the live memory engine (project `<project-ref>`).
Nothing was edited, migrated or deleted. Every finding below was reproduced
against live data or the live code; anything that could not be reproduced is
in **Suspicions** at the end.

**What was reviewed.** The live Postgres functions and data match the **v3**
migration (`20261031100000_memory_engine_v3.sql`) on branch
`claude/wonderful-mccarthy-gujuq1` (commit `05b4dab`, 21:28 UTC today), not
the v2 code on `main`. The seven edge functions v3 touches were all redeployed
21:57–21:58 UTC. Findings therefore target v3; where main differs it is called
out. Data at review time: 58 `memory_items` rows (47 active), 2 users,
4 companions, all rows `importance 5`, `confidence 0.7`, `source inferred`,
and **0 rows with an embedding**.

## Summary (the five biggest problems)

1. **Vector retrieval has never run and the lexical scorer is miscalibrated**: 0 of 58 rows have an embedding (including rows written minutes before the v3 deploy), and the term-share relevance formula leaves 28 of 41 eval turns with no row above the 0.2 gate, so for ~70% of turns the prompt gets "the 5 most recently extracted facts" regardless of what the user said.
2. **A denied fact is broadcast to every companion and nothing can correct it**: `User is an author` is the only global row, the user denied it twice, the denial is stored as a friend-scoped thread, and the v3 extractor emits zero correction ops for the user's actual correcting message (3 of 3 runs). v3 also removed the only path that used to fix this in-band.
3. **The extractor closes unrelated open threads** on roughly half of emotional or new-topic messages (sister's birthday closes the six-pack thread; a bereavement closes the mind-opening goal). The grounding check cannot catch it because the quoted evidence is the whole message.
4. **The repository is not the source of truth**: `main` ships v2 (RRF retrieval) while production runs v3 (term-share retrieval, unique index, forget/clear RPCs) from an unmerged branch, and neither v2 nor v3 is recorded in `supabase_migrations`. Tuning or testing against `main` measures the wrong engine.
5. **Architecture caps quality regardless of tuning**: candidates are the 500 most recently updated rows (older facts become unreachable), the "background" tier is pure recency because importance/confidence are constants, MMR diversity outweighs relevance when scores span 0.08, and dedupe cannot fire without vectors or a shared stemmer.

**Baseline: 28 / 41 pass.** Full per-case output: `results/results_2026-10-26.md`.

## Findings (ordered by impact)

### 1. Embeddings are never written; vector retrieval is dead and fails silently

**Severity: high.** Everything the design calls "semantic" (vector search, the
vector half of dedupe, synonym recall) is inert, and nothing reports it.

**Evidence.**
- `select count(*), count(embedding) from memory_items` → 58, 0. Rows created today at 18:25–18:26 UTC have `embedding NULL, embedding_model NULL`.
- `dream-hygiene` ran at 03:00 UTC on 10-25 and 10-26 (`cron.job` `0 3 * * *`, function logs) and embedded nothing. `embedTexts()` returns `null` on any failure by design ("never throws"), so there is no error line in `function_logs` and no counter anywhere; the only observable is the backlog itself.
- Eval G01 ("how do I get abs?") has relevance 0 for every six-pack row because no row contains the token `ab`; this is exactly the case vectors exist for.

**Proposed fix.** Make the degradation loud: log at `error` with the HTTP status when `embedTexts` fails, return `{embedded, backlog}` from dream-hygiene and alert when `backlog > 0 && embedded == 0`, and expose `count(*) where embedding is null and status='active'` in the admin console. Then fix the cause (see Suspicions: the key is almost certainly missing from the edge-function secrets).

**Test against the eval set.** Run `run_eval.mjs --supabase --embed` once rows are embedded: G01 must gain `include_any`; F04 / F14 / F15 / G06 must stay `no_relevant`.

### 2. The relevance gate almost never fires, so retrieval is recency

**Severity: high.** With no vectors, relevance is `n_hit / n_terms × min(1, n_hit/2)`. A direct question that shares one exact, rare word with a five-term memory scores 0.1 and never clears the 0.2 gate. The prompt is then filled from the "background" tier, which is ordered by blended score, which with constant importance and confidence is ordered by recency.

**Evidence** (live `content_tsv` term breakdown):

| case | query → memory | shared terms | memory terms | relevance |
|---|---|---|---|---|
| M01 | "When is my deadline again?" → `User has set a goal deadline of end of November` | 1 (`deadlin`) | 5 | 0.10 |
| F02 | "Did I ever finish that series?" → `User recently completed reading an entire series` | 1 (`seri`) | 5 | 0.10 |
| F13 | "What should I read next now that I'm done?" → same row | 1 (`read`) | 5 | 0.10 |
| G02 | "should I try intermittent fasting?" → `User is considering fasting as a method for body fat reduction` | 1 (`fast`) | 6 | 0.083 |

28 of 41 eval turns had **no** row at or above 0.2. Six vague turns (F07, F09, F14, F15, M06, M11) and five specific turns (F02, F06, F11, F13, M01) injected the identical "five newest" set for their pair. M01 passes only because the deadline row is currently among the five newest; it will fail as soon as five newer facts exist.

**Proposed fix.** Weight terms by rarity instead of counting them: use `ts_rank_cd(content_tsv, query, 32)` or an IDF-style weight computed over the user's own rows, so one exact rare term (`deadlin`, `fast`) is a strong match and shared common terms (`seri`, `read`, `book`) are weak. Drop the half-credit-for-one-word rule for rare terms. Make the gate relative: if any row has relevance > 0, take the top-k by relevance before falling back to background.

**Test.** M01, F02, F13, G02 must each produce relevance ≥ 0.2 for the named row; F04, F14, F15, G06 must stay `no_relevant`; F07 and M06 must not gain relevant rows.

### 3. A denied fact is global, injected everywhere, and has no correction path

**Severity: high.** `User is an author` (`2d796bfd`, scope `global`, companion `NULL`) is wrong: one minute after it was stored the user said "I'm just reading the series", and correction events `f4e17d66` and `5e59279a` recorded "User is reading the Ice Cream Social series, not the author". The correction was written as a **friend-scoped thread** (`7698b3ce`); the wrong fact stays **global**.

**Evidence.**
- Eval: `2d796bfd` was injected in M04, M05, M11, F03, F05, F13 (and as background in most other U2 turns). In M05 ("am I an author?") it is the top result with relevance 0.5.
- Live `memory_turn_trace`: `User is an author` appears in every traced turn for both of this user's companions (10-19, 10-22, 10-24, 10-25, 10-26).
- Six further active friend-scoped rows assert authorship or the wrong title (`bb144c46`, `6193f04a`, `2040b4ea`, `37f5fd70`, `c44a1f30`, `9c428adf`).
- Mechanism: `supersede_memory_item` inherits the target's `companion_id`/`scope`, so a correction can only ever replace a row the current companion can see; the extractor only sees F-ids for this pair's rows; dream-hygiene processes pairs and auto-applies a supersede only when a `correction` event points at that exact `memory_item_id` (the 10-19 events point at threads, not at the fact).

**Proposed fix.** (a) Corrections must follow visibility: when an update/retract targets a row, also match global rows about the same subject (token overlap ≥ 0.6 or vector match) and supersede them with the same scope. (b) Store corrections as facts with `source user_stated` and `importance ≥ 8`, never as threads. (c) Human one-off: retire `2d796bfd` and the six authorship rows; they are in `/admin/memory-proposals` only indirectly.

**Test.** M04, M05, M11 must exclude `2d796bfd`; F03 must include `7698b3ce` (or its fact replacement) and exclude the five authorship rows.

### 4. The extractor does not correct implicit contradictions, and v3 removed the fallback

**Severity: high.** v3 made the extractor "the one write path for corrections" and reduced the post-response analyzer to logging. The extractor does not take the bait on the user's real correcting sentence.

**Evidence** (`run_extractor_eval.mjs`, claude-haiku-4-5, the exact chat-turn prompt and tool):
- E01: stored list includes `F2 [fact] User has written a book that is a murder mystery series…`, `F8 … has written a murder mystery series where the protagonist owns an ice cream shop`, `F3 User's book is called an 'Ice Cream Social book'`, and the global `User is an author`. Message: *"I'm just reading the series. It's pretty amazing."* → **zero fact ops in 3 of 3 runs** (one run emitted a malformed `thread:confirm`, which chat-turn ignores).
- The v1 analyzer did catch this message (correction event `f4e17d66`, confidence 0.92, "User is reading the Ice Cream Social series, not the author"); under v3 that event is only logged, and dream-hygiene only acts on it if the LLM pass independently proposes the same target id.
- Live memory_events: 3 `correction` events, 0 superseded rows that resulted from them.

**Proposed fix.** Keep one write path, but feed it: when the analyzer logs a `correction` with `memory_item_id` (v3 already restricts ids to those shown) and `corrected_content`, enqueue a deterministic `supersede_memory_item` with the user's quote as evidence, or re-invoke the extractor with an explicit "the user said X contradicts F3" hint. Add a prompt example of an implicit correction ("I'm just reading it" vs "has written").

**Test.** E01 must produce `update`/`retract` on at least one authorship row in ≥ 2 of 3 runs; add an SQL regression: after a correction event with a known id, the target is not `active` within one hygiene run.

### 5. The extractor closes unrelated open threads

**Severity: high** (silent data loss on the follow-up system).

**Evidence** (same probe, three calls per message):
- E05 *"my sister Maya is turning 30 next week and I'm flying to Denver for the party"* with the six-pack thread open → `thread:close T1 (0cea7222 "Six-pack abs and fitness approach")` in 2 of 3 runs.
- E10 *"my dad passed away yesterday, I am not ok"* with the mind-opening goal thread open → `thread:close T5 (99b9d99a "Mind-opening exercises goal … end of November")` in 2 of 3 runs.
- In every case the evidence string is the entire message, so `isGroundedIn` passes; nothing checks that the evidence relates to the thread being closed.
- Supporting live signal: thread `ee029703` ("Books and reading — recently completed a book") was closed at 20:31:29 on 10-19 by the v1 analyzer while the user was still elaborating on the book.

**Proposed fix.** For `close`, require lexical overlap between the thread's content tokens and the evidence (≥ 1 non-stopword token, or `isGroundedIn(threadTopic, message)`), and record a `thread_close_proposed` event instead of retiring on the first signal; retire on the second consistent signal or when `due_at` has passed. Add a negative example to the prompt ("a new topic does not close an old thread").

**Test.** E05 and E10 must produce zero `close` ops; add a positive case ("I finished the series!" with the reading thread open) that must close exactly that thread.

### 6. The repository does not describe production

**Severity: high** for everything downstream (tests, evals, incident response).

**Evidence.**
- Live `pg_get_functiondef('fetch_memories_for_turn')` uses `v_qlex` term-share scoring; `main`'s `20261030100000_memory_engine_v2.sql` uses reciprocal rank fusion. Live has `uq_memory_items_active_text`, `forget_memory_item`, `clear_user_memory`, `retire_expired_memories`, `claim_unsummarized_messages`; main has none.
- Those objects exist only in `20261031100000_memory_engine_v3.sql` on branch `claude/wonderful-mccarthy-gujuq1` (commit `05b4dab`, 21:28 UTC), which is not on `main`.
- `supabase_migrations.schema_migrations` lists neither v2 nor v3 (last entries are `20261030120000_status_posts_and_feed`, `20261031120000_world_visits_and_card_details`); the memory migrations were applied outside the migration history.
- `docs/memory-engine.md` on `main` documents RRF retrieval that is not what runs.
- The 23-check SQL regression on `main` would pass against a database that production no longer resembles.

**Proposed fix.** Merge the v3 branch (or revert production to v2); record the applied migrations (`supabase migration repair --status applied 20261030100000 20261031100000` after confirming); add a CI check that compares `md5(pg_get_functiondef(...))` of the memory RPCs against the repo's migrations; put `git rev` into each edge function's response headers or logs.

**Test.** `run_eval.mjs --emit-sql` output executed on a scratch database built from the repo must produce the same `candidates` JSON as production for the fixture.

### 7. MMR diversity outweighs relevance and recency

**Severity: medium.** `selectMemories` uses `value = 0.7·score − 0.3·maxJaccard`. Scores span 0.27–0.76 in theory but 0.29–0.37 for almost every row, so a 0.5 Jaccard overlap (0.15 penalty) beats any realistic score gap (≤ 0.05).

**Evidence.** F13: `95ff4a7c` "recently completed reading an entire series" (score 0.361, newest, correct) was dropped; `cac97d53` "plans to read the entire series" (0.366, stale) was kept; then `2040b4ea` "User's book is called an Ice Cream Social book" (0.297, wrong) and `03316fc0` (0.297) were chosen because they share fewer tokens. F01 picked `6193f04a` ("has written…", rel 0.056) over `d50e79f2` (rel 0.333) for the same reason.

**Proposed fix.** Min-max normalise `score` over the candidate set before MMR (so the 0.7/0.3 trade-off means what it says), or apply the diversity penalty only between items in the same relevance tier, or treat `isNearDuplicate` as the only diversity mechanism and set λ = 1.

**Test.** F13 must include `95ff4a7c` and exclude `cac97d53`; F01 must exclude `6193f04a`; F09 / M02 must keep `max_dupes ≤ 1`.

### 8. "Background" context is the five newest facts, including wrong and stale ones

**Severity: medium.** Design challenge: the background slots were meant for pinned, identity-level context. Because every live row has `importance 5` and `confidence 0.7`, the blended score is `0.55·rel + 0.15·recency + 0.17`, so with `rel = 0` the background is purely "most recently extracted".

**Evidence.** F07, F09, F14, F15 inject the same five rows; M06 and M11 the same five; R01 and R03 inject `User is currently with a girl` seven days after the evening it described (the row has no `valid_until`; v1 stored it as durable, and v3's extractor produced no op at all for the same message in E04, so nothing will ever expire it). Baseline cost of a turn with nothing relevant: 120–205 memory tokens.

**Proposed fix.** Background eligibility = `source in (user_stated, user_edited)` or `importance ≥ 7` or `confirm_count ≥ 2`; otherwise inject nothing. Add a one-off hygiene rule: rows whose text contains `currently | right now | tonight | today | this week` and no `valid_until` get `valid_until = created_at + 2 days` (would retire `ccaea324`).

**Test.** R01 and R03 must exclude `ccaea324`; F07 and M06 token counts must drop; M01, M07, R02 must still pass.

### 9. Hygiene destroyed information and its dedupe cannot fire

**Severity: medium.**

**Evidence.**
- Under v2's auto-apply rule, dream-hygiene on 10-26 03:00 retired the user's actual goal `User is interested in developing a six-pack` (`807c4b6c`, proposal `8e3d5c3d`, rationale "generic parent fact… subsumed") and the newer, progressed thread "…Now ready to formally set a goal with timeline" (`ba33d204`, proposal `d11f38af`) as a duplicate of the older thread. The goal now exists only inside thread `0cea7222` (eval G03/G04). v3 narrows auto-apply to past-due threads and explicit corrections, which fixes the rule but not the data.
- Deterministic dedupe produced **zero** proposals on 10-25 and 10-26 (all 24 proposals come from the LLM pass) despite nine paraphrases of the mindset goal and seventeen rows about one book. Reason: `isNearDuplicate(strict)` needs Jaccard ≥ 0.75 on a home-made stemmer (`creative` vs `creativity` do not collide; Postgres stems both to `creativ`), and the vector branch is off (finding 1).
- The LLM pass failed to parse for the friend pair on 10-26 (`[dream-hygiene] Failed to parse proposals for 9cb333ea…:0fde7eaa…`), i.e. for the pair with the largest duplicate cluster; it is a free-text JSON array capped at 2000 output tokens.

**Proposed fix.** Compute dedupe keys in SQL from `content_tsv` (same stemmer as retrieval) and fold rows whose stemmed sets have Jaccard ≥ 0.75 and no `mayContradict`; switch the hygiene LLM call to forced tool-use like the extractor and size `max_tokens` to the item count; add `memory_proposals.after` for every retire so the kept row is recorded.

**Test.** Run `findDuplicateGroups` over the fixture's U2_MENTOR rows: expect ≥ 3 groups; F09/M02/M11 `max_dupes ≤ 1` must hold with 12 facts selected instead of 5.

### 10. Scale ceiling: the 500 most recently updated rows are the only rows that exist

**Severity: medium** (not hit today; certain at 10–100×).

**Evidence.** The `eligible` CTE is `ORDER BY updated_at DESC LIMIT 500` before any scoring. Synthetic 5,000-row pair (CTE shadowing `memory_items`, nothing written): the unique fact "User's daughter is named Hikaru…" was unreachable (`hikaru_reachable = false`, best relevance 0) and only 84 of 834 rows mentioning hiking were reachable. Latency is fine (7.5 ms real plan, 35 ms at 500 eligible rows) — the problem is recall, not speed. The HNSW index is also never used: filtering happens first and the distance is computed per row.

**Proposed fix.** Retrieve relevance-first: a GIN-backed `content_tsv @@ query` candidate set plus an HNSW top-k (`ORDER BY embedding <=> q LIMIT 50` with the user filter; at per-user volumes exact scan is also fine), union, then score; keep "newest N" only as the background pool.

**Test.** The synthetic SQL in this review (`hikaru_reachable` must become true); add a 600-row fixture pair to the eval with one old unique fact.

### 11. Privacy: third parties, over-sharing, and residual text

**Severity: medium.**

**Evidence.**
- E11 *"my coworker Dana told me she's pregnant but hasn't told the boss yet, keep it between us"* → extractor writes durable `person` fact `User's coworker Dana is pregnant` plus a thread. Nothing in the pipeline distinguishes facts about the user from confidential facts about others.
- E05/E09: `shareable: true` on a sibling's birthday and a job change; with `shared_memory_consent` these become global rows that every companion (and Atlas, which now reads `memory_items`) sees. That is the documented intent, but there is no per-fact user review before a fact goes global; today the only global row is the wrong one (finding 3).
- v3's `scrub_memory_items` is thorough for rows in the supersede chain, but correction events whose `memory_item_id` is `NULL` (e.g. `5a8f8f8f`) keep their payload, and `memory_proposals.rationale` often quotes other rows' text and is not scrubbed.

**Proposed fix.** Extractor rule: facts about named third parties are stored as relationships ("User has a coworker named Dana"), never their health/legal/financial state, and never shareable; add a `sensitivity` column and exclude `sensitive` from background slots and from `shareable`; scrub `memory_proposals.rationale` and payloads by text match, not only by id.

**Test.** E11 must produce no durable fact containing "pregnant"; extend the forget SQL checks to proposals' rationale.

### 12. Observability gaps

**Severity: low.** `memory_turn_trace` stores injected ids and token counts but not the query text, the relevance/score of each injected row, or whether a vector was used; `embedTexts` failures are invisible (finding 1). Debugging any of the above in production requires replaying the turn.

**Proposed fix.** Add `query_text`, `used_vector`, and `[{id, relevance, score}]` to the trace; emit one structured log line per turn.

### 13. The companion summary has never been produced

**Severity: low.** `summarize-memory` fires at 50 unsummarized messages per pair; the busiest pair has 37, so all 122 conversations are unsummarized and there are 0 `moment` rows. The "semi-stable" summary block the design relies on for prompt caching is empty for every user.

**Proposed fix.** Trigger on time (e.g. nightly if ≥ 10 new messages) as well as on count.

## Suspicions (not reproduced)

- `OPENAI_API_KEY` is missing from the edge-function secrets. Consistent with 0 embeddings over 17 days and no error logs; could not confirm because the management API denied `edge_functions_secrets_read`.
- The dream-hygiene parse failure on the friend pair is output truncation at `max_tokens: 2000`; the raw model output is not logged.
- `memory-mutate` `edit` to text that normalises to another active row would hit `uq_memory_items_active_text` and surface as a 500; untested because it needs a write.
- No chat turn has run since the v3 deploy (last user message 18:27 UTC, deploy 21:57 UTC), so `evidence`, `last_confirmed_at`, `durable: true` and the restricted analyzer ids are unobserved in production.
- The legacy client stack (`semanticMemoryService`, `relationship_memories` — 0 rows) is still reachable when `USE_SERVER_PROMPT` is off; not traced.
- With a key present, the 1.5 s read-path embedding timeout may be hit on cold edge instances; no data.

## Could not check

Edge-function secrets; the deployed function bytes (inferred as v3 from deploy timestamps and the database state); `private`-scope behaviour (no private rows exist); real multi-user volume (only synthetic scale).

## Reproducing

```
# SQL stage on the live DB (read-only), then selection + scoring:
node --experimental-strip-types scripts/memory-eval/run_eval.mjs --emit-sql > /tmp/eval.sql
# run /tmp/eval.sql (psql or the SQL editor) and save the single JSON cell as results/candidates_<date>.json, or:
node --experimental-strip-types scripts/memory-eval/run_eval.mjs --db-url "$DATABASE_URL"
node --experimental-strip-types scripts/memory-eval/run_eval.mjs --candidates scripts/memory-eval/results/candidates_2026-10-26.json

# write-path probe (no writes):
ANTHROPIC_API_KEY=... node --experimental-strip-types scripts/memory-eval/run_extractor_eval.mjs --runs 3
```

Pass `--engine <path>` to point at a different `memoryEngine.ts` (this review
used the v3 copy from commit `05b4dab`; `main`'s v2 copy differs in thresholds
and the negation guard).
